Executive takeaway. This spec designs the “sequenced” in-place upgrade — backup → offline → swap → hydrate → start — as a small, externalized tool that ships in the NeuroStrata repository but never becomes part of the daemon. The core is a Rust binary, neurostrata-cutover (new workspace crate crates/cutover), with thin shell entry points under scripts/migration/. The tool is deliberately engine-free: it never links LadybugDB; it probes file headers, hashes files, and orchestrates the old and new daemon binaries through a gated phase machine (precheck → backup → swap → hydrate → post-validate → close-out/restore). It does not re-implement backup or restore: the daemon already ships a canonical snapshot facility (the /backup route and CLI backup) and a canonical restore (CLI restore); the crate drives those and layers on top what they lack — checksum verification before restore, out-of-rotation export, gating, the content oracle, sequencing, and the run record (§3.2A). Every claim the sequence relies on is one this lane has measured: conversion happens at the new engine’s first checkpoint, downgrade past that point is restore-only, and the unverified-WAL fallback silently recovers nothing — so the tool treats that fallback as a hard stop, never a recovery path, and pins the environment of every daemon it spawns so the fallback cannot be armed by an operator's shell (§3.5). A full rehearsal mode runs the identical code path against a disposable store copy. Approval of this design unlocks the upstream issue (§9); it authorizes no push, no PR, and no execution against any live daemon.

1. Purpose and scope

Problem. Upgrading a NeuroStrata daemon across a LadybugDB storage-format boundary (here: lbug 0.20.4 writes storage v47; 0.22.3 writes v49 and converts a v47 store at its first checkpoint) is a one-way door with a silent-failure mode in the middle. Done by hand it depends on operator memory for ordering, verification, and rollback semantics. This tool makes the sequence repeatable, validated before and after, rehearsable, and honest about where the point of no return sits.

In scope.

  • The cutover tool: orchestration, pre-validation, post-validation, rehearsal, restore, and a durable run record — layered over the daemon's own snapshot/restore facilities (§3.2A).
  • Upgrade pairs of the same shape as 0.20.4 → 0.22.3: single-writer file store, checkpoint-time conversion, older binary fails closed on the newer format. Expected from/to storage versions are parameters, not constants — the design's most general element, foregrounded in the upstream issue (§9).
  • Linux operators (systemd user service, or an ad-hoc daemon process) and macOS (process mode; offered as a trimmable scope item in the upstream issue, §3.4). Windows: out of scope for v1 (§3.4).

Out of scope.

  • Executing a cutover against any live daemon. Provisioning and rehearsing the tool is this program; running it live is a separate, per-target authorization.
  • Hot-swap. The options evaluation proved it not viable (statically linked engine, exclusive store lock for the daemon’s life, hardcoded client endpoint); the best achievable is the pre-staged short-gap restart this sequence already produces (an evaluation estimate of roughly 2–10 minutes — §4, Timing).
  • Changes to the daemon runtime (src/). Externalization is a hard design constraint (§2, P8). The crate drives the daemon's shipped CLI and routes; it adds no daemon code.
  • The “Case B” preconditions for any specific production daemon (storage-version census of that store, supervision inventory). The tool’s rehearsal mode is the vehicle for those checks; the checks themselves belong to the target’s own runbook.

2. Design principles

IDPrincipleWhat it means here / evidence anchor
P1Engine-free orchestrationThe tool never links or embeds LadybugDB and never opens a store with an engine. It reads file headers, hashes files, and drives the two daemon binaries as external actors. A validator linked to one engine version inherits that version’s refusal modes; header- and file-level facts are version-independent. The boundary is enforced at linkage and at the child-process environment (§3.5) — the live boundary is the environment a spawned daemon inherits.
P2No engine opens of originals; no writes to the live store (boundary unified in v2)The prohibition is precise: (i) no engine — old, new, or the tool's own subprocesses — ever opens the live store except the daemon binaries in sequence order; (ii) the tool never writes into the store directory. Read-only byte reads of the live file (header version word) are permitted and required by the hydrate watch, under a double-read agreement rule (two consecutive reads must agree, else retry; persistent disagreement is a NO-GO/STOP, never a guess). Where a phase needs a full copy of a running store, the source is the daemon's own snapshot (§3.2A) — never an operator-improvised cp of a live, writing store, which can present a torn, mid-checkpoint header.
P3Every transition is gatedNo phase starts until the previous phase’s exit criteria are recorded as passing in the run manifest. Gates are re-probed at execution time (§4, S0 staleness rule) — a gate passed on Tuesday is not a gate passed on Friday. A failed criterion is a stop with a named state, not a warning to blow past.
P4Hard stops, not fallbacksMeasured on both engine versions (Tasks 4b/4c): on a checksum-failed WAL, the unverified fallback reports success and recovers nothing. Therefore: strict-WAL refusal, backup checksum mismatch, or the unverified-recovery marker in a daemon log is an automatic abort to a named safe state. The tool contains no code path that “recovers” by discarding a WAL, and §3.5 keeps the fallback from being armed by environment inheritance in the first place.
P5Stop is proven, not inferredA daemon counts as stopped only when all three hold: the store lock (<db_path>.daemon.lock) is free (an flock probe, the daemon's own daemon_holds_lock mechanism), the lock file's final-checkpoint report reads checkpointed (the daemon writes this report into its lock file at shutdown; the CLI shutdown verb reads it back), and no process holds the store file (§3.2, supervisor — holder enumeration that fails closed when the mechanism is unavailable). Never port silence or process exit alone (evaluation condition C7). If the checkpoint report is absent or reads error: …, the stop is recorded as unproven-checkpoint: the S1 set is then treated as WAL-bearing (valid, because the WAL is in the set) and the manifest says so — never silently upgraded to “checkpointed”. The repo’s scripts/backup.sh embodies the file-holder doctrine via lsof but treats a missing lsof as a pass; this design explicitly does not adopt that fail-open limb (Panel B9).
P6Rollback honestyThe tool names the rollback mode at every phase — in-place (old binary can still open the store), restore-only (after the first new-engine checkpoint), or none — and never labels a restore as an in-place rollback; the subcommand is named restore, not rollback (§3.1). Two distinct traps are kept distinct (v2, Panel A8): (a) the verify-open trap — CLI restore verifies its copy by opening it with the invoking binary's engine, so restoring with the new binary would convert the restored copy on close; S5 therefore drives restore with the old binary (§4 S5). (b) the refusal-inference fallacy — inferring a restore is v47 from the old binary's refusal to open something else proves nothing (Task 4 Case 3: refusal leaves bytes unchanged); S5 proves the set is v47 by checksum against checksums.json before any engine runs, and by header probe after.
P7Rehearse everythingEvery phase runs against a disposable store copy through the identical code path (evaluation C2/D1) — identical including the exit-code surface (§6.3). Rehearsal is a first-class mode, not a test-only hack; rehearsing against the configured live store path is refused outright (§3.2, run lock).
P8Externalized; zero runtime changesThe deliverable is one new workspace crate plus files under scripts/migration/ and docs. No changes under src/. The daemon under upgrade is a black box with a CLI, routes, and a store directory (§2A).
P9Secrets stay putThe tool never reads token contents at all: the two credentials (§5, B16) live in daemon.token (bearer) and operator.token (operator class, for the destructive routes /backup and /shutdown) under ~/.config/neurostrata/, and are consumed only by the daemon's own client code when the tool drives the shipped CLI. Continuity is proven by successful authenticated calls, not by comparing secret bytes. Config and token files are never written by any phase — with exactly one sanctioned exception, named here so it cannot hide: the S5 restore repoint of db_path in config.json, performed as a recorded, backed-up step because the shipped restore deliberately leaves that edit to the operator (§4 S5; reconciles evaluation C4's “config/token files untouched” with restore's shipped semantics).
P10Drive, don’t duplicate (new in v2)One canonical implementation per concept (maintainer Rule 10). Where the daemon already ships a facility — snapshot, restore, snapshot checksum format, the shutdown/status verbs — the crate drives or consumes it and adds only the missing layer (§3.2A). A second implementation of an existing concept requires a named, specific lack, stated in the design or the plan — not a preference.

2A. Store location and file set (new in v2 — Panel B2)

Locating the store. The daemon reads db_path from ~/.config/neurostrata/config.json (Config::default_path); when the file is absent the compiled default is ~/.config/NeuroStrata/data/db/ladybug.db. If db_path names a directory, the daemon appends ladybug.db (Config::load_from). The tool resolves the store exactly as the daemon does — same file, same defaulting, same directory rule — then canonicalizes to an absolute path before any probe. If db_path is relative, it is resolved against the working directory the supervisor will launch the daemon with (the systemd unit's WorkingDirectory, or the recorded launch context in process mode) and the resolution basis is recorded in the manifest; a relative path whose basis cannot be determined is a NO-GO, never a guess — the daemon (systemd CWD) and the tool (operator shell CWD) resolving one relative path to two different stores is the failure this rule exists to prevent.

The live file set. For store file F (absolute), the set is defined by census against these members:

MemberNotes
FThe database file itself (default name ladybug.db).
F.walThe live write-ahead log; may be absent. Data-bearing beside a header-only db in the un-checkpointed case — it is always in the set when present.
F.daemon.lockThe daemon's flock file; at shutdown its contents become the final-checkpoint report (checkpointed / error: …). In the census for observation; excluded from backup hashing (it is mutated by design) and from the B4 equality gate's hash set (its census presence is compared, not its bytes).
F.wal.unclean.<unix-secs>Preserved copies of an unclean shutdown's WAL, made by the store's preserve_unclean_wal at open (zero or more). Forensic assets: censused, carried in backups, never deleted by the tool.
F.wal.corrupted.<unix-secs>Leftovers of a failed unverified-retry per docs/runbooks/wal-recovery.md (zero or more). Same treatment.

Any other sibling matching F.* is recorded in the census as unrecognized; an unrecognized sibling appearing or disappearing mid-run is a manifest/reality disagreement (§4, resume). Set membership is always by census at phase time, never by assumption.

The snapshot set. A daemon snapshot (§3.2A) is a directory containing: ladybug.store, ladybug.store.wal (optional — a post-checkpoint WAL rides along when one exists), manifest.json ({format: "neurostrata-snapshot", version: 1, created_at, source, bytes}), checksums.json (sha256 of ladybug.store, of the WAL when present, and of manifest.json), and optionally manifest.json.zst. This is the daemon's published format; the crate consumes it, it does not redefine it.

sequenceThe phase machine and the run record. Enforces P3 gates and P4 hard stops; tracks the rollback mode as phases advance (P6); holds the per-store run lock (an flock on a lockfile in the run-record directory, keyed by store-path hash) for the whole run — a second invocation against the same store is refused with the holding run's ID, and rehearse against the configured live path is refused outright (Panel B8).Contains no engine knowledge beyond the parameterized expected storage versions.
hydrateAfter the new daemon starts: poll the store header (read-only, P2 double-read rule) for the version flip, scan daemon logs for hard-stop markers, and timestamp the conversion event — the point of no return — into the run record. Log sources are pinned at S3 entry: systemd → the unit's journal from the S3 start timestamp; process mode → the stdout/stderr the adapter captured to a run-scoped log file at spawn. If neither source is complete, V-POST-05 cannot pass as VERIFIED (Panel B15).Does not force a checkpoint by writing to the store. Checkpoint triggering is a distinct, deliberate act with its own decision framing (§4 S3, Panel C2) — not a hydrate reflex.
oracleProduce a canonical content dump of a store and compare two dumps. Production: drive a daemon binary (the new binary in both directions — engine-consistent, independent of the old engine's historically broken EXPORT path) against a sacrificial copy of a snapshot set, take its EXPORT DATABASE output, and canonicalize it (below). The sacrificial copy is created from the verified snapshot set solely for this purpose and is destroyed after; it is never the backup set itself — wiring the oracle to the backup set would convert the rollback asset to the to-version at the copy's first checkpoint, discovered only when S5 reaches for it (Panel B6). Canonicalization (canon: 1): the dump's file set is enumerated at production time and recorded; any unexpected file fails the oracle step. For each exported table file (sorted by file name): parse records, sort records byte-wise by rendered primary key, render one record per line with pinned field rules — strings UTF-8 with escaping (\\, \n, \r, \t, other control characters as \uXXXX), integers decimal, floats in a pinned round-trip rendering fixed by the canon version, timestamps in UTC ISO-8601. A schema block (table names + column names/types, sorted) is hashed separately from the record block, so a schema change reports distinctly from a record divergence. Scope: the oracle covers exactly the exported content surface; state outside it (derived index/vector state, runtime metrics) is out of oracle scope by enumeration in §5.2, cross-checked cheaply by a namespace census (V-POST-03b). Determinism is a gating test, not an assumption (§8): if byte-hash determinism fails on a production-shaped fixture, V-POST-03 degrades to the fallback comparison named in §5.2.Never dumps the live store directly, never dumps the backup set, and never claims “content identical” beyond the exported surface it enumerates.
statusRead-only rendering of run state (Panel C3): current phase, rollback mode now, last gate results with their VERIFIED/ATTESTED class, and the legal next actions — from the run record plus fresh probes. Takes no run lock; tolerates a torn record tail (§6.2). Usable mid-phase and post-crash, without invoking any mutation-path command.Changes nothing; refuses nothing; it only reports.

3.3 Deployment

  • New workspace member crates/cutover (the workspace already carries one member, crates/neurostrata-wasm); binary name neurostrata-cutover. Built and released with the repo’s normal build; operators need only the binary plus the wrappers.
  • Configuration is flags + environment (store path or config path, both binary paths, snapshot staging + out-of-rotation destinations, expected from/to storage versions, supervision mode). No config-file format is invented in v1.
  • Run-record directory (Panel C4): default $XDG_STATE_HOME/neurostrata/cutover/, else ~/.local/state/neurostrata/cutover/; per store, a subdirectory keyed by store-path hash holding the run lock and one record per run. Follow-up commands (validate, restore, --resume, status) bind by explicit --run <id>, else to the store's single in-progress run; two in-progress runs for one store cannot exist (run lock, §3.2).
  • A CI guard enforces P1: the crate’s dependency tree must not contain lbug (a test greps the locked dependency set — scoped to the shipped binary's normal dependency tree, Panel C17). If the tree grows an engine edge, the build fails.

3.4 Platform scope (v1)

  • Linux: full support — systemd-user adapter and process adapter.
  • macOS: process adapter only (no systemd); the sequence, probe, snapshot/restore driving, and oracle are platform-neutral; holder proof depends on lsof and fails closed without it (§3.2). This adapter doubles the supervisor test surface with no macOS-operator evidence in the record; it is offered as a trimmable item in the upstream issue (§9) — the maintainer's call, surfaced rather than assumed (Panel C16).
  • Windows: out of scope for v1. The Rust core is portable, but supervision (services, file-holder proof) and the bash entry points are not; the adapter interface is the named extension point. Stated plainly so no operator mistakes the tool for a Windows offering. Symmetrically, nothing in v1 CI verifies the crate's platform-cleanliness (§8) — the claim is aspirational until a leg exists, and the design says so (Panel C14).

3.5 Environment contract (new in v2 — Panel B7)

The daemon's store-open ladder is environment-sensitive: NEUROSTRATA_ALLOW_UNVERIFIED_WAL=1, or NEUROSTRATA_STRICT_WAL=0, arms the unverified-WAL fallback that P4 exists to hard-stop (strict_wal_verification() in the store). An operator shell, a wrapper's exported defaults, or a systemd unit carrying either variable from unrelated debugging would defeat P4 while every gate passes. Therefore:

  • Every process the tool spawns or drives — CLI backup/restore subprocesses, oracle opens, the S3 start in process mode — runs with a pinned environment: NEUROSTRATA_STRICT_WAL=1 forced, NEUROSTRATA_ALLOW_UNVERIFIED_WAL removed, NEUROSTRATA_PRUNE_SNAPSHOTS removed (snapshot hygiene must not prune the rollback asset mid-run, §6.4), and a named strip-list applied to anything else WAL- or store-related. The effective environment class (strict forced: yes) is recorded in the run record per spawn.
  • Systemd mode: the tool does not rewrite the unit's environment in v1. The gate is a predicate: read the unit's effective environment (systemctl show); if either WAL variable arms the fallback, S0 is a NO-GO until the unit is fixed. A predicate, not an attestation (Panel C5).
  • The oracle path is inside this contract explicitly: an oracle open under a tainted environment could replay a checksum-failed WAL unverified, checkpoint the sacrificial copy, and produce a clean hash of a store that silently dropped writes — after which V-POST-03 would compare two identically tainted dumps and pass.

4. The sequence — phase machine

Phases run in order; each lists its exit criteria (all must pass and be recorded) and its failure exit. GATE = criteria checked before proceeding · STOP = hard stop to a named safe state (§4.2).

Staleness rule (Panels B13/C4). 4.1 The gap guard (new in v2 — Panel B1)

The hazard window is S1-stop → S3-start, and it has named intruders: an MCP stdio client reconnecting during the gap auto-spawns the binary at its configured path (the new binary after S2 — unmanaged, outside the sequence, holding the lock when S3 starts); a CLI invoked in the gap, after the lock frees, opens the store directly and becomes the writer — if it is the new binary, its close checkpoints and converts the store before S3's conversion watch exists. Defences, in order:

  1. Re-verification at the stop: client-quiet (V-PRE-07) is re-checked as part of S1's stop step, not inherited from a possibly days-old S0.
  2. Window watch: from the S1 stop until S3's start completes, the tool polls the store lock and the header version word every 2 s. Any lock holder appearing in the window, or the header flipping outside S3, is a GAP-INTRUSION stop (§4.2) — the run does not proceed against a store someone else has touched.
  3. Holder identity at S3: the first lock holder after S3's start must resolve to the recorded new-binary hash and be the adapter's own spawn; anything else is named and stopped.
  4. Reality-ahead conversion: if a stray new-binary spawn nevertheless converted the store before S3 (detected: header already at to-version at S3 entry), the run does not fabricate an in-phase conversion event. The record states “conversion observed at S3 entry, unattributed”; S4 runs in full; the acceptance owner decides with that provenance on the table.

5. Validation catalogs

Gate results carry a class: VERIFIED (a predicate was executed) or ATTESTED (an operator claim where no predicate exists). Attestation is fallback only, never co-equal (Panels A4/C5): an attestation record must state (i) the specific thing not verified, (ii) why it cannot be verified, (iii) who attests, (iv) the obligation it creates. Every downstream rendering — status, validation report, the sealed run record — shows ATTESTED distinctly; an attestation that renders identically to a passed check is a failed check wearing a costume. Credentials are named per step (Panel B16): the operator token (with the bearer) authorizes the destructive-class routes (/backup, /shutdown); the bearer token authorizes ordinary authenticated calls. The tool handles neither token's contents (P9) — the shipped CLI's own client code reads the token files.

8. Testing strategy

  • Banked fixtures — provenance pinned (Panels B10/C17). A v47 store can only be produced by an old-engine (0.20.4) build; once the bump merges, no in-repo script can regenerate one, and a fixture generator pinned to lbug 0.20.4 inside the workspace would fight the P1 guard and silently rot. The supply is therefore banked binary fixtures, committed now, with a fixture manifest recording producer engine (lbug 0.20.4, from the 2026-11-08 upgrade run) and per-file sha256: the clean v47 store (172,032 B), the WAL set (4,096 B header-only db + 15,790 B WAL, content hash 22c8999f…), and the Task 4b corrupted-WAL variant (exactly 1 byte at offset 925) as the negative fixture. These are test inputs with explicit provenance — the opposite failure shape from a generated artifact masquerading as source-of-record. Any future fixture is produced by driving a hash-pinned daemon binary in a test-harness prerequisite step outside the shipped crate (the P1 guard scopes to the shipped binary's normal dependency tree); the harness-step mechanics are an implementation-plan item, the rule and the prohibition are pinned here.
  • The 200k-row store is never committed (78,790,656 B). Its crash-during-conversion coverage lives in the dispatch-only E2E venue (below) using the lane-banked fixture, hash-pinned and held outside the repo. Stated coverage loss: in-repo CI does not re-run the 200,000-row kill-during-checkpoint case; that case remains evidenced by Task 4 and re-runnable in the E2E venue.
  • Determinism gate for the oracle (Panels A6/C8). Byte-for-byte determinism of the canonical dump is a gating test, not an assumption: a regenerated multi-table, edge-bearing fixture (produced by driving the daemon binary in the harness prerequisite step) is dumped twice (must be identical) and dumped again after conversion (must be identical).
