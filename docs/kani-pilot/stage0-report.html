NeuroStrata Kani Pilot — Stage 0 Report

Seeding and setup, as authorized by the owner on 2026-11-17 · Prepared 2026-11-17 · Census basis: upstream Cognilogical/NeuroStrata main @ dd1affef (v1.18.1)

Governing spec: the verification-frameworks panel judge's verdict §5 (2026-11-16) and completeness audit gaps G1/G2. Stage 0 time-box: 2 working days. This report is the Stage 0 deliverable; Stage 1 begins only on the owner's ruling.

Stage 0 outcome: the gate passes, and the subject is the secrets scanner (src/secrets.rs). The defect census (100 fix commits, classified) confirms the auditor's suspicion and sharpens it: the defect stream is dominated by sequential logic (SEQ 29%), but only 1 of 100 defects is a clean Kani catch as the code stands — the rest manifest through the FFI store, the async daemon, or integration seams. The pilot therefore lives or dies on subjects whose sequential core is already the shipped code. The secrets scanner is exactly that: a pure synchronous core that already carries escaped sequential defects of its own (a panic in pure string code, two matcher-logic defects), needs no extraction, and guards the highest-blast-radius write surface in the system. Pre-registered metrics, kill criteria, the equivalence-bridge design, and the CI lane design are filed with this report.

1. What Stage 0 had to produce

Per the judge, Stage 0 exists to close the audit's two blocking gaps before any verification spend: G1 — no defect census (the pilot subject was an assumption, not a finding) — and G2 — no equivalence bridge (a verified copy would recreate, at pilot scale, the model-fidelity gap the panel charged against Aeneas). Five preconditions: (1) the census plus an existing-controls inventory; (2) a subject census and a selection made from it, with no pre-commitment; (3) the G2 design — refactor-in-place plan, extraction ceiling, trusted-boundary register, atomics/threads census of the subject; (4) pre-registered success/kill metrics, including a seeded-defect non-vacuity check; (5) a CI lane design against the repo's actual workflows. If Stage 0 cannot close G1 and G2, the pilot dies automatically.

The headline the panel predicted, confirmed with numbers: the historical defect mass is not a concurrency population, and it is not directly provable either — 69 of 100 defects have a sequential core but manifest through integration. A Kani pilot pointed at the code as-is would catch almost nothing. The pilot's only honest shape is the judge's: pick a subject whose sequential core is the shipped code, and verify that.

Existing controls (the baseline any adoption must beat)

2,176 test functions (1,416 #[test] + 760 #[tokio::test]), all example-based, run single-threaded in CI; CI jobs cover build (3 OSes), test, plugins, scripts, and cargo-audit — with no clippy, rustfmt, Miri, or sanitizer jobs, and no property, fuzz, or concurrency-testing tooling anywhere (no proptest/quickcheck/bolero/loom in the manifests; no fuzz/ directory; no #[kani]). The one existing formal control is a Lean 4 proof tree with parity tests, covering parts of the formal kernel and taxonomy. (The panel-era count of 1,083 tests was taken on an older tree with a narrower count; the fresh census basis above supersedes it.)

Selection rationale, in one paragraph. The secrets scanner is the only candidate that satisfies every term of the judge's selection rule at once: the census shows it carrying a bounded, sequential, escaped-defect class (a panic in pure code; matcher false negatives and false positives — predicate logic, Kani's home ground); its blast radius is the highest of the pure cores (credentials at rest, propagated by mesh sync); and its extractability is not a promise but a present fact — the shipped functions are the core, so refactor-in-place, the G2 gate, is satisfied by construction. One honesty note: of its four census defects, the wiring defect (scanning not invoked on two paths) is not something Kani on the core would have caught — verification of the core proves the scanner's decisions, not its invocation. The pilot claims the other three.

4. Equivalence bridge (G2)

Filed in full as state/g2-bridge-design.md. The design in brief: harnesses live in a #[cfg(kani)] module inside src/secrets.rs and call the production scan_str/scan_value functions directly — the verified code is byte-for-byte the shipped code, a single source of truth. Permitted production edits in Stage 1 are visibility widening and cfg(kani) harness hooks only, under a zero-behaviour-change evidence rule (the full 2,176-test suite stays green). The bounded-envelope honesty clause is stated in the design: proofs run at a shrunk input envelope (≤128-byte strings, depth ≤4) while production caps are 256,000 bytes / depth 8; behaviour at production bounds rests on the cap-enforcement path and the example tests, and no report may claim otherwise. Atomics/threads census of the subject: zero in production logic; the two OnceLock immutable lookup statics are carried as register item T1. The trusted-boundary register is opened with four entries (T1 OnceLock tables, T2 the input envelope, T3 floating-point entropy modelling, T4 a pattern-engine inventory owed at Stage 1 start) under the rule that an item is registered before it is relied on.

5. Pre-registered metrics (G9)

Filed in full, frozen, as state/pre-registration.md — before any Stage 1 work, as required. The binding numbers:

  • Ceilings: verified core ≤ 1,200 production LOC; ≤ 40 harnesses, all Bolero dual-use style; CI advisory lane ≤ 15 minutes; refactor diff extraction-only with zero behaviour change.
  • Success (all required): shipped code is what is verified; all harnesses pass with unwinding assertions passing; atomics gate holds; all five pre-registered mutants are caught (pattern-predicate inversion, JWT boundary off-by-one, metadata-key branch deletion, entropy-threshold weakening, placeholder-exemption removal) — a surviving mutant voids the green, one repair cycle allowed; CI ceiling held; results reported with produced/verified splits and the full register.
  • Kill (any one, no fallback): refactor-in-place infeasible or verify-a-copy becomes the only route; the subject can't be isolated from async/FFI/Drop/atomics without becoming a different component; either time-box or the CI ceiling is exceeded; success would need the unstable contracts path or an unregistered assume/stub; the seeded-defect check fails after one repair cycle; the census basis materially changes mid-pilot.
  • On a kill, the census and the dual-use harnesses (re-expressed as property/fuzz tests) remain as deliverables of the alternatives-first stack. On success, any wider use is a new decision. The stack is sequenced first because it covers the actual risk surface — it is not assurance-equivalent to proof, and no wording in this programme says otherwise.

6. CI lane design (G7)

Against the actual workflows at the census basis (ci.yml: build/test/test-report/plugins/scripts/audit/release-references; no clippy or fmt jobs): the pilot adds nothing to ci.yml. A separate kani.yml workflow runs the lane on ubuntu-latest (x86_64; architecture covered by any proof: x86_64-unknown-linux-gnu), with Kani pinned and installed only inside that job — the shipping toolchain is never touched. Triggers: PRs touching src/secrets.rs plus a weekly run. The lane is advisory (not a required check; failure uploads its JSON/SARIF report as an artifact and does not block merge), with a 15-minute job timeout per the pre-registration.
