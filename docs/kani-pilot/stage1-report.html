Stage 1 execution is complete. Under the frozen success criteria, the pilot cannot be declared "succeeded" — and no kill criterion fired either. The judgement is the owner's, on the exact split below. 13 Kani harnesses were produced; 9 verified with zero failed checks, and 4 could not be verified on this machine (solver timeouts and CBMC memory exhaustion — never a property failure). Frozen success criterion 2 requires all harnesses to pass, so it is not met as written. Against that: the pre-registered non-vacuity check passed in full — all five seeded mutants were caught, two of them by Kani harnesses directly — and the dual-use design the judge mandated did exactly its job, carrying the properties Kani could not reach onto executable tests. The headline technical discovery: Kani 0.68 cannot compile the regex crate at all (an internal compiler error), so everything above the extraction seam is outside proof scope for this toolchain, a fact now registered as T4-S1 rather than worked around.

4. Trusted-annotation register (final state)

  • T1 — Two OnceLock immutable statics (scanner singleton; base64 table). The base64 table path is inside a verified harness; the singleton sits above the regex seam and was never constructed under Kani.
  • T2 — Harness input envelope (bounded strings/values). All verified results are concrete-battery or bounded-form results; no claim is made at production input bounds (256,000 bytes / depth 8).
  • T3 + T3-S1 — Entropy: shannon_entropy_bits_per_char stubbed at three constant values bracketing 4.2 for the threshold-decision harnesses. The threshold decision is verified modulo the stubbed entropy value; the entropy computation itself rests on example tests. Filed before use, as the register rule requires.
  • T4 + T4-S1 — The regex extraction seam, resolved by evidence: Kani 0.68 ICEs compiling the regex crate, so extraction and everything above it (scan_inner, scan_str, detect_jwt's matching phase, the AKIA branch) is outside proof scope and rests on the example-test suite. Not stubbed, not worked around.
  • T5 — scan_inner oracle for Tier 2 structural harnesses (rejects iff the text contains a planted marker). Tier 2 properties cover scan_value_inner's traversal only. Uses Kani 0.68's unstable -Z stubbing; the CI lane carries the same flag.
  • T6 — Fabricated SecretScanner receiver for Tier 2 (concrete-zero bytes, never dropped, fields never read by the callee — auditable in source). The entry documents three abandoned fabrication attempts before this device was relied on. If scan_value_inner ever reads a receiver field, T6 is void and Tier 2 must be re-derived.

One process incident is on record in the log: an over-broad cargo fmt mid-run reformatted 143 files; it was fully reverted and the tree re-verified to the intended diff before proceeding.
  • Environment note: local runs required ORT_LIB_LOCATION/ORT_PREFER_DYNAMIC_LINK=1 against a local ONNX Runtime (the ort-sys prebuilt download is blocked in this sandbox). The CI lane needs neither.

6. CI lane

.github/workflows/kani.yml is committed on the branch per the Stage 0 design: separate workflow, ubuntu-latest (x86_64), Kani 0.68.0 pinned via cargo install kani-verifier --locked, advisory (not a required check), 15-minute timeout, triggers on PRs touching src/secrets.rs plus a weekly run, enumerating only the 9 verified harnesses. Ceiling risk, recorded plainly: the verified set sums to ~13 minutes on this VM; GitHub's runners are faster per-core but the margin under the 15-minute ceiling is thinner than the design assumed. If the lane times out in practice, that is a ceiling breach under the pre-registration, not a tuning detail.
