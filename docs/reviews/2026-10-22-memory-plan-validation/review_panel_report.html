▶ Bound the production buffer pool P0 VERIFIED CONSENSUS src/store/ladybug.rs:605-607, 707-709 · lbug database.cpp:52-70

Narrative

Production opens the store via LadybugStore::new → verifying_config(), which sets only throw_on_wal_replay_failure(true). The underlying SystemConfig::default() leaves buffer_pool_size: 0, which the engine resolves to 80% of physical RAM (DEFAULT_PHY_MEM_SIZE_RATIO_FOR_BM = 0.8), and max_db_size: u32::MAX, which resolves to an 8 TB virtual region. The test path deliberately bounds both to 64 MiB / 512 MiB — its own doc comment cites an "8 TiB" mmap reservation. Production does not.

Code evidence

// lbug-0.20.4/lbug-src/src/main/database.cpp:52-70
if (bufferPoolSize_ == -1u || bufferPoolSize_ == 0) {
  auto systemMemSize = _SC_PHYS_PAGES * _SC_PAGESIZE;
  bufferPoolSize_ = 0.8 * min(systemMemSize, UINTPTR_MAX);
  bufferPoolSize_ = min(bufferPoolSize_,
      DEFAULT_VM_REGION_MAX_SIZE * 0.8);
}
if (maxDBSize == -1u)
  maxDBSize = DEFAULT_VM_REGION_MAX_SIZE;   // 1<<43 = 8TB

Judge ruling

The ceiling is not an allocation — the pool fills as pages are touched. But it is unbounded by configuration and scales with installed RAM. Bound it and measure; do not assume it is currently dominant. This is the highest-ceiling, lowest-risk change in the set.

Fix

Add a config field, plumb it into SystemConfig for both the verified and unverified paths, keep throw_on_wal_replay_failure(true) on the normal open, and add a production read path for the sizing (today only NEUROSTRATA_TEST_* exists, read solely inside for_testing()).

▶ Ingest clears before embedding and swallows failures P0 EXISTING_DEFECT src/parser/ingest.rs:544-553, 490-507, 518

Narrative

ingest_directory calls clear_ingested(namespace) before the walk begins. Per-symbol embed and upsert failures only eprintln!, and the function returns Ok(()). The plan's headline recommendation — make the remote embedder the default — converts an edge case into a routine one: a network blip empties a namespace's code index and the command exits 0.

Code evidence

vector_store.clear_ingested(namespace).await.map_err(...)?;   // :544
...
Err(e) => eprintln!("Failed to embed symbol {} ...", ...),     // :499
...
Ok(())                                                          // :518

Fix

Stage the ingest and swap on full success; propagate embed/upsert failures. Must land before any change that increases embed failure rate.

▶ Establish a measured baseline first P0 PLAN_RISK src/main.rs:1747-49, 1874-85

Narrative

The plan's "523 MB" evidence is a model cache comment, not resident memory. cargo bloat measures binary size; ps is a point-in-time snapshot that may include the proxy; ingest --help exits during clap parsing before build_embedder() is ever reached.

Fix

Measure the daemon PID only. /usr/bin/time -l for peak; vmmap <pid> (macOS) or /proc/<pid>/smaps_rollup (Linux) for the resident/virtual split. Sample after startup, after first inference, after a fixed ingest, and after idle — so "high while idle" and "grows and never returns" can be told apart.

▶ Remote 429/5xx retry never fires P1 EXISTING_DEFECT src/embed.rs:242 vs 267-271

try_embed returns a plain anyhow string for HTTP errors, so e.downcast_ref::<reqwest::StatusCode>() in embed_with_retry can never match. The backoff branch is dead code.

Fix

Return a typed error carrying the status, or match on the response before converting.

▶ Any embedder change needs a schema + re-embed migration P1 PLAN_RISK src/store/ladybug.rs:1431-1437 · README.md:299,303

The column is embedding FLOAT[{dimensions}], fixed at table creation and sized from the embedder's declared width. No embedder identity is persisted, and no re-embed command exists. Switching 768 → 384 shatters the schema; switching to a same-width model silently mixes incompatible vector spaces. The README already ships a 1536-dim remote example against 768-dim local defaults — one config edit from breaking.

Fix

Persist embedder identity + width, refuse startup on mismatch, and provide an explicit re-embed path before any model change.

▶ Keep remote embedding opt-in, not default P1 PLAN_RISK src/embed.rs:48-63, 303

Defaults are local; remote needs both base_url and api_key_env. Making it default exports every ingested symbol's source text to a third party, adds a network dependency to startup, and — combined with the P0 ingest defect — turns a blip into data loss.

▶ Proposed tokio feature list would not compile P1 PLAN_RISK Cargo.toml:11 · src/server.rs:5,1356-1364 · src/daemon.rs:601,1044-1068

full enables fs, io-util, io-std, macros, net, parking_lot, process, rt, rt-multi-thread, signal, sync, time. The proposed subset omits fs, io-util, net and signal, all used. And it would not reduce memory even if it compiled: thread counts come from Builder::new_multi_thread() at main.rs:1733-1740, not from cargo features. If thread memory is implicated the lever is max_blocking_threads.

▶ Keep MAX_EMBED_TOKENS = 2048; do not lower to 512 P1 PLAN_RISK src/embed.rs:124-126 · src/parser/ingest.rs:31

The code's own ratio is ~3.5 chars/token, so 4000 chars needs ~1143 tokens. 512 covers ~1792 chars and would silently truncate the majority of a maximal symbol — a recall regression, not a memory win. Token count does not change weight residency; it only affects the activation peak when inputs exceed the cap.

If shrinking is required

Lower stored text and token cap together, and measure retrieval quality.

▶ Drop BlobStore from the plan — no production caller P1 VERIFIED src/learning/blob_store.rs:11,28 · mod.rs:15

The Mutex<HashMap<PayloadHash, Vec<u8>>> is genuinely unbounded, but the only uses are the definition, a re-export, and #[cfg(test)] sites. Bounding it cannot reduce current daemon RSS.

▶ Keep the Mutex; batching raises peak memory P2 PLAN_RISK src/embed.rs:129,180

TextEmbedding::embed needs &mut self (the code binds let mut guard), and ORT sessions are not safe for concurrent run. A read guard will not compile; a write guard serializes exactly like the Mutex. Batching is a throughput change that raises peak: one [1,2048,768] f32 tensor ≈ 6 MiB, so batch 32 ≈ 192 MiB.

▶ FETCH_MULTIPLIER is a query cost, not an RSS cost P2 src/store/ladybug.rs:46, 52-53, 86-89

The stringified 768-float query vector is ~10 KB and transient. Reducing the multiplier can return fewer than limit domain-matching rows — preserve filter semantics and profile before changing.

▶ Prune finished ingest jobs; fix lane numbering P2 src/ingest_jobs.rs:135,178 · PLAN.md:84-85

The jobs map inserts but never removes. Separately, the plan's "lanes 1+2+3" names lane 4 and omits lane 3 — split the rollout into independently measurable, revertible commits.

Coverage gaps

  • ORT arena high-water retention is never discussed — it decides whether this is a "grows and never returns" problem or an "idle is high" problem.
  • Daemon lifecycle: periodic restart as a bounded-ceiling lever is not considered.
  • The learning-laya feature is decorative (Cargo.toml:63-65); no cfg(feature = …) exists, so gating it changes binary size, not RSS.
  • No target RSS and no rollback path were ever defined.
